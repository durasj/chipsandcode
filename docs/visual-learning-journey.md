# The visual learning journey

## Model and interaction (chosen before implementation)

The course uses two linked SVG views: **Inside this piece** explains each task's composition or behavior; **Place in the computer** preserves that piece's label while revealing its role. The journey sits in the main learning flow above construction. Its topic browser can inspect any earlier or later step without unmounting the active editor. Returning to the challenge restores the active scene; no inspection awards progress.

The outside view is a recognizable computer frame with supplied keyboard and display. It receives all evidence, fills the corresponding branches as work is verified, shows reusable pieces by name inside their parent modules, and leaves unverified parts dashed. A completed piece retains its label as it shrinks into the larger context. The hardware model branches. Logic supplies word operations and arithmetic; routing plus clocked state supplies memory. The branches meet at the CPU and memory interface. Instruction ROM, mapped data memory, the supplied keyboard, and supplied screen form the connected computer. Assembly is a representation translated into ROM words, never a physically larger shell surrounding hardware. DFF, NAND, ROM32K, Screen, and Keyboard are labeled supplied where relevant.

Every introduction concept, gate mission, and Project 1–6 task has explicit journey metadata in `src/lib/journey/data.ts`. Distinct layouts show parallel lanes, reduction/routing trees, carry propagation, state feedback, memory banks, instruction fields, and the connected machine. Explicit connected graph models cover gate composition, half/full adders, ALU preprocessing and selection, bank decoding and read multiplexing, CPU control/data paths, PC priority, loops, and assembler passes. Arrows carry data or control; no generic dangling component stubs stand in for these relationships. Desktop and mobile use separately arranged graphs with legible labels. The coverage table below is generated from that metadata and tested against the real curriculum. This avoids a milestone list silently missing small steps.

### State and triggers

- A new task selects its own composition, context, and next capability. Within a layer the structure changes (for example four to eight routes or one to sixteen stored bits).
- A verified task reveals the wider system with the same component identity. Verification is derived only from existing course/mission completion data; opening an advanced lesson never awards previous work.
- Introduction stages report observed behavior separately from built circuits. NAND is characterized, not fabricated.
- The scene accepts actual part names from the active draft and live pin values when available. The internal teaching diagram is explicitly a conceptual composition, not a claim to reproduce every valid learner circuit.
- Revisit controls affect only the scene. A separate explicit lesson link navigates; drafts retain the existing save behavior. Page reload uses the existing task/progress selection. A saved completion is identified as previously verified; editing still requires a fresh check.
- A short reveal runs on task or verification change. Replay and skip are available. Reduced motion presents the exact same final diagram, explanatory text, and controls without motion. No timeout, animation, or browsing controls progression.

### Runtime payoff

A small runtime panel reuses `HackMachine`, the assembler, and the existing `Screen` component. The supplied example reads KBD, selects a fill value, and writes screen memory by executing instructions. The learner can load their Fill source into the same panel. The display is always drawn from actual screen words. Read and write trace facts explain the causal path: keyboard → CPU/program → screen memory → pixels. The assembler view exposes the same source → machine word → executed machine relationship.

### Alternatives

A 3D engine would add navigation and accessibility cost without explaining logical relationships better. A literal matryoshka zoom would misrepresent the arithmetic/memory branches and software. A small breadcrumb would miss the requested central experience. SVG and native HTML reuse the site's restrained typography, violet signals, dark surfaces, and responsive controls; text equivalents carry the same information.
